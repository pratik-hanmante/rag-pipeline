What are we building?

A RAG pipeline: a program that answers questions about your own documents by finding the relevant passages first and then asking an AI model to answer using only those passages.

RAG stands for Retrieval-Augmented Generation. Retrieval means finding the right text. Augmented means adding that text to the prompt. Generation means the LLM writes the answer.

Analogy: an open-book examAn LLM on its own is like a student answering from memory. It may not know your company's refund policy, so it might guess. RAG hands the student the right pages of the textbook first, so the answer comes from those pages and can cite them.
The pipeline, step by stepclick any step
A · INGEST: runs once per document, in the background
B · QUERY: runs every time someone asks a question

Three ideas you need

  • Chunk. A small piece of a document, a few paragraphs long. We split documents up because a whole PDF is too big to paste into a prompt, and most of it is irrelevant to any one question.
  • Embedding. A list of numbers (1536 of them for OpenAI's model) that represents what a piece of text means. Texts with similar meanings get similar lists of numbers, even if they use different words. In Python terms it's just a list[float].
  • Vector search. To answer a question, turn the question into an embedding too, then find the chunks whose embeddings are closest to it. "Closest" is calculated with math, usually cosine similarity, which you'll get to play with in Chapter 4.
Chapter 1

Setting up the Python environment

Before writing any code, we needed an isolated place to install packages. That's a virtual environment (venv): a folder with its own copy of Python and its own site-packages, so this project's packages don't clash with other projects'.

Decode the commandsclick each piece

Problem 1: “no such file or directory”

(base) rag-pipeline % python3 -m venv venv          # creates a folder named  venv
(base) rag-pipeline % source .venv/bin/activate     # looks for a folder named .venv
source: no such file or directory: .venv/bin/activate
What went wrongThe folder was created as venv, but the command tried to activate .venv, with a dot at the start. Those are two different names. A leading dot also makes a folder hidden in macOS, so .venv and venv are both common conventions. Just be consistent.
Fixsource venv/bin/activate. Your prompt then shows (venv).

Problem 2: Python 3.14 was too new

(venv) % pip install -r requirements.txt
  ...building pydantic-core from source...
error: the configured Python interpreter version (3.14) is newer than
       PyO3's maximum supported version (3.13)
Failed to build tiktoken pydantic-core
What went wrongSome packages, such as pydantic-core and tiktoken, are written partly in Rust for speed. pip normally downloads a pre-built version called a wheel. The pinned 2024 versions have no wheel for Python 3.14, so pip tried to compile them itself. Their build tool (PyO3) didn't support 3.14 yet, so the build failed.
FixWe deleted the empty venv and recreated it with the Python 3.11 from the curio conda environment, then installed again. All 18 packages installed and import correctly.
% rm -rf venv
% /opt/homebrew/Caskroom/miniforge/base/envs/curio/bin/python -m venv venv
% venv/bin/pip install -r requirements.txt
Successfully installed ... fastapi-0.115.0 ... sentence-transformers-3.1.1 ...
% venv/bin/pip check
No broken requirements found.

What “(venv) (base)” in the prompt means

(base) means conda's base environment is active, and (venv) means your project venv is active on top of it. The venv wins, since its python comes first on your PATH, but having both active can be confusing. Run conda deactivate first to keep things clean. Use which python to check which Python you're using. It should print …/rag-pipeline/venv/bin/python.

Chapter 2

The 18 packages in requirements.txt

requirements.txt is a shopping list for pip. fastapi==0.115.0 means "exactly this version", and asyncpg>=0.29.0 means "this version or newer". Pinning exact versions makes sure everyone gets the same setup. Click a card for an explanation, an analogy and a code sample.

Square brackets = extrasuvicorn[standard] means "uvicorn plus its optional speed-up packages". sqlalchemy[asyncio] means "SQLAlchemy plus what's needed for async/await". That's why pip installed about 90 packages in total: each package brings its own dependencies. For example, sentence-transformers pulls in PyTorch.
Chapter 3

Docker: running Postgres and Redis

Our app needs two servers: PostgreSQL (the database) and Redis (the job queue). Instead of installing them on your Mac, we run them in containers. A container is a small, isolated Linux box that holds just that one program. docker-compose.yml describes both boxes, and docker compose up -d starts them.

Python analogyA venv isolates Python packages. A container isolates a whole program and its operating system. Delete the container and your Mac stays clean.
docker-compose.yml, line by lineclick a line
% docker compose up -d      # start both containers in the background (-d = detached)
% docker ps                 # list running containers → rag-pipeline-db-1, rag-pipeline-redis-1
% docker compose down       # stop them (data survives in the volumes)
Chapter 4

The database schema

schema.sql defines two tables. Think of each table as a list of rows, where each row is like a Python dataclass instance with fixed, typed fields. Click a column to see what it's for.

documents → chunks1 document has many chunks

Try it: chunking

The ingest worker cuts each document into overlapping pieces. The overlap matters: if a key sentence falls on a boundary, it still appears whole in at least one chunk. Move the sliders.

Real code counts tokens with tiktoken, not words. One token is roughly ¾ of an English word, and typical settings are 300 to 800 tokens per chunk with 10 to 15% overlap. Underlined words are shared with the previous chunk.

Try it: vector search

Below, six chunks from a pretend company handbook are drawn as arrows. Real embeddings have 1536 numbers each. These have 2 so we can draw them. Pick a question to see which chunks point in nearly the same direction.

    Score = cosine similarity: 1.0 means the same direction (same meaning), 0 means unrelated. In SQL, pgvector's <=> gives cosine distance = 1 − similarity, so ORDER BY embedding <=> :q puts the closest chunks first. The 3 highlighted chunks are what gets sent to the LLM.

    Why the schema also has content_tsv (keyword search)Vector search finds meaning, so "money back" matches "refund". It can miss exact strings like error codes (ERR-4021) or product names. content_tsv plus its GIN index give fast keyword search too. Combining the two is called hybrid search.
    Why the HNSW indexComparing a question against every chunk is fine for 1,000 chunks and slow for 10 million. HNSW builds a graph of "neighbour" vectors, so the search can jump straight to the right area. It's approximate, but finds nearly all of the true nearest matches. m=16, ef_construction=64 are pgvector's default settings.

    Creating the tables

    We fed schema.sql into the Postgres server that runs inside the Docker container. Click each piece of the command:

    (venv) % docker exec -i rag-pipeline-db-1 psql -U rag_user -d rag_db < schema.sql
CREATE EXTENSION   ← pgvector switched on
CREATE TABLE       ← documents
CREATE INDEX       ← unique (tenant_id, content_hash): no duplicate uploads
CREATE TABLE       ← chunks
CREATE INDEX       ← chunks.document_id
CREATE INDEX       ← chunks.tenant_id
ALTER TABLE        ← added content_tsv column (keyword search)
CREATE INDEX       ← GIN index for keyword search
CREATE INDEX       ← HNSW index for vector search

    Each line is Postgres confirming one statement from the file. No line starting with ERROR: means everything worked. If you run the file a second time, you'll get ERROR: relation "documents" already exists. That's harmless and just means the tables are already there.

    % docker exec -it rag-pipeline-db-1 psql -U rag_user -d rag_db   # open an interactive SQL prompt
rag_db=# \dt              # list tables
rag_db=# \d chunks        # show columns + indexes of chunks
rag_db=# SELECT count(*) FROM chunks;
rag_db=# \q               # quit
